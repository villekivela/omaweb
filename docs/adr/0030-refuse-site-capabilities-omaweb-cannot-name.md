# Refuse site capabilities Omaweb cannot name

Site capabilities are decided from an allow-list of named policies rather than from whatever the engine happens to ask about. A capability Omaweb has no policy for is refused without a question being asked: a question whose only honest answer is no is not a question, and an engine that grows a new capability must not be able to reach the reader through Omaweb before Omaweb has decided what the answer means.

This refines [ADR 0009](0009-separate-browser-policy-from-engine-mechanics.md). The three Site-permission decisions there — allow once, persistent allow, block — remain, but they are what a *rememberable* capability offers. Camera, microphone, geolocation and notifications are rememberable. Clipboard read and screen sharing are asked every time and no answer is written down, because each hands over whatever is on the screen or on the clipboard at that instant, which no earlier answer could have covered; offering to remember one would be the reader agreeing to a use they will never be shown again. Adapters translate the engine's own capability identifiers into these names, so the policy is written in Omaweb's words and an untranslated identifier is refused rather than asked about.

Certificate failures block. Omaweb offers the reader an exception only where the engine reports the failure as overridable and not fatal, in the main frame, for a Local-development site. Everything else — a fatal failure, a subresource or a frame, a public site, a page nobody is looking at — is refused without a question, and Omaweb never offers to remember one: nothing about a granted exception reaches a disk, so the next session asks again. There is no remembered-exception store to add later; adding one would be reversing this decision, not extending it.

Within a session, the exception is the engine's to hold and Omaweb cannot take it back. QtWebEngine records an accepted certificate in its profile's own SSL host state and exposes no way to revoke it, so from the next load onward the engine raises nothing and reports the connection as secure. Omaweb therefore keeps its own record of which origins have a waived check — in memory, for one Space, for one session — and the address trigger reports a certificate error for as long as that record stands, in every tab of that Space. The alternative is an adapter's silence being read as a check that passed, which is the one reading a security indicator must never allow. An adapter clears its own report when a load arrives with no failure raised for it, because a certificate that has since been fixed is not a waived one; distinguishing the two is the shell's, from its record, not the adapter's.

Third-party cookies and third-party site storage are blocked. An authentication or payment flow may be given one origin's allowance inside one Space: it lives in memory beside the Site permissions a shared private session already passes between its windows, is listed in Site information with the flow it was granted for, and is revocable there. Nothing about it is written to disk, so it cannot cross a Space or outlive the session that granted it, and Omaweb never infers that a flow is a sign-in — the reader names the origin and the purpose.

Active mixed content stays blocked and there is no release path that turns the blocking off. A launch switch that would lower a web security boundary browser-wide is a refusal to start, whether it arrives on the command line or through the environment's engine flags, because nothing the reader can see on a page would tell them the boundary had been given away.

Nothing an engine decides for itself may put a site's decisions beyond the reach of the reset that is offered for them. QtWebEngine stores granted permissions in a profile of its own by default and answers a later request from that store without asking the embedder, which would make Omaweb's own reset appear to work and change nothing. Engines are therefore told to ask every time, so Omaweb's store is the only place a site's decisions live, and an origin's reset drops the engine's own record of it as well. What remains outside reach is a capability a loaded page is already holding: engines answer that from a store keyed by the frame that asked, and reloading reuses the frame, so Site information says that opening the site again is what takes it back rather than offering a reload that would not.

Site data is cleared at whichever scope the engine can actually reach, and the reader is told which that is. Engines expose no per-origin removal at their embedding boundary — QtWebEngine wires Chromium's own remover for the cache alone — so cookies and cache are taken for a whole Space, and the confirmation says so before it happens. One origin's storage, databases, caches and service workers are reachable from inside its own document, so that clearing is asked of the page and reports what it managed to empty; cookies are not, because the ones that matter are unreadable from script. Neither action is described as the other, and a size is only ever counted against the action that can move it.

Where the engine cannot answer for part of this contract, Site information says so rather than drawing a reassuring blank. Reporting a certificate failure at all and refusing a third party are named capabilities an adapter may lack. How much site data a Space holds is not a capability: it is measured on disk at the path Omaweb assigned the engine's profile, and is shown only where the adapter claims to keep a persistent profile.
